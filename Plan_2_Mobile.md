# План реализации (v2): Мобильный офлайн-переводчик Русский ↔ Северокорейский (Munhwao)

> Документ фиксирует итог «прожарки» идеи и заменяет устаревшие разделы Plan_1.md
> в части платформы, серверной архитектуры и тестирования. Пайплайн «Корейского моста»,
> золотой стек репозиториев и правила пост-обработки из Plan_1.md остаются без изменений.

## 0. Зафиксированные решения (из диалога)

| # | Решение |
|---|---------|
| 1 | Лицензионные ограничения не рассматриваем — считаем закрытыми |
| 2 | Целевая платформа: **только Android** (iOS — позже). Десктопов нет |
| 3 | Полностью **локальный инференс на телефоне**, без интернета и без серверов |
| 4 | Приложение для начальника и рабочих стоит **на каждом телефоне**; набрал → перевёл → показал экран |
| 5 | Лексика — обычный разговорник + производственные ситуации, без узкой специализации |
| 6 | Разработка **не затрагивает рабочих**: никаких фото, голосовых, опросов. Обратная связь — только в процессе эксплуатации готового продукта |
| 7 | Ввод корейской стороны — **встроенная в UI виртуальная клавиатура** с северокорейской раскладкой (не системная раскладка телефона). Реальной схемы раскладки нет — делаем произвольную, потом заменим |
| 8 | Голосовой ввод (ASR) в MVP **нет** — моделей под munhwaо не существует |
| 9 | Модели — **квантованные (INT8 / ONNX)** для экономии памяти телефона |
| 10 | Автотесты: **round-trip RU→NK→RU** на длинных предложениях (15–20 слов) + самоулучшение по ходу |

## 1. Что меняется относительно Plan_1.md

1. **Убираем FastAPI / локальный сервер / `python -m http.server`** (Этап 5 п.2, Backend из раздела 6). Всё крутится внутри APK.
2. **Python-стек заменяется на мобильный рантайм:** модели конвертируются в ONNX и выполняются через ONNX Runtime Mobile; токенер/пост-обработка — Kotlin. Альтернатива-страховка — встроенный Chaquopy (Python-in-APK), но она раздувает APK, поэтому основной путь — ONNX.
3. **MeCab/handic (этап 4) не переносятся на телефон в лоб** (C++ с python-обвязкой). Замена: морфологический разбор направления NK→SK на устройстве делаем словарно-regex слоем (jamotools-логика переписывается на Kotlin: декомпозиция слога хангыля на джамо — это чистая арифметика Unicode), а тяжёлый анализ оставляем в офлайн-конвейере подготовки данных.
4. **Требования к железу пересчитаны под телефон** (раздел 3).

## 2. Архитектура приложения (Android)

```
┌────────────────────────── APK ──────────────────────────┐
│  UI (Kotlin/Jetpack Compose)                            │
│   ├─ Два поля ввода/вывода + кнопка смены направления   │
│   ├─ Встроенная виртуальная клавиатура (2 раскладки:    │
│   │    русская + северокорейская-хангыль)               │
│   └─ История фраз (локально, SQLite)                    │
│                                                        │
│  Переводческий слой (Kotlin)                            │
│   ├─ PipelineRunner: RU→SK→NK и NK→SK→RU               │
│   ├─ ONNX Runtime Mobile (инференс всех 3 моделей)      │
│   ├─ Токенизаторы (реализация BertTokenizer/SentencePiece│
│   │    на Kotlin или через onnxruntime tokenizers)      │
│   └─ PostProcessing: dict.json (Samhung/Biyak/dict.js)  │
│        + regex -습니다→-습네다, -입니다→-입네다          │
│                                                        │
│  Assets (распаковываются при первом запуске)            │
│   ├─ ru2sk.onnx (quant INT8)                           │
│   ├─ sk2ru.onnx (quant INT8)                           │
│   ├─ sk2nk.onnx + nk2sk.onnx (KoBART quant INT8)       │
│   └─ словари JSON, таблицы раскладки                    │
└────────────────────────────────────────────────────────┘
```

Два экземпляра приложения (начальник / рабочий) ничем не отличаются — направление перевода переключается кнопкой. Прямой передачи данных между телефонами в MVP нет: «показал экран».

## 3. Расчёт памяти и места на телефоне (квантованные модели)

Оценка «на пальцах» по PLAN.md-весам (fp32 → int8 ≈ ÷4):

| Модель | FP32 | INT8 ONNX | RAM при инференсе |
|---|---|---|---|
| opus-mt-ru-ko (~75M) | ~300 МБ | ~75–90 МБ | ~250 МБ |
| opus-mt-ko-ru (~75M) | ~300 МБ | ~75–90 МБ | ~250 МБ |
| KoBART SK→NK (~125M) | ~500 МБ | ~130–150 МБ | ~400 МБ |
| KoBART NK→SK (~125M) | ~500 МБ | ~130–150 МБ | ~400 МБ |
| Словари/токенеры/прочее | — | ~50–100 МБ | ~100 МБ |
| **Итого на диске** | | **≈ 0.6–0.8 ГБ** | |
| **Итого пик RAM** (модели грузим по одной под направление) | | | **≈ 0.7–1.2 ГБ** |

Выводы:
* **Минимум для комфортной работы: Android 10+, 6 ГБ RAM, 4 ГБ свободного диска.**
* На 4 ГБ RAM тоже запустится (грузим только нужные две модели направления), но впритык.
* Если качество opus-mt окажется недостаточным — замена базовой пары на NLLB-600M INT8: +~150 МБ на диске, +~0.8–1 ГБ RAM-пика → тогда требование растёт до 8 ГБ RAM.
* Скорость на Snapdragon 7-й серии / Dimensity 8000+: 0.5–2 сек на предложение (decoding на CPU/GPU NNAPI).

Точные цифры проверяются на Этапе M0 (замер после первой конвертации) — это первый же артефакт проекта.

## 4. Встроенная клавиатура с северокорейской раскладкой

* Это **не IME системы Android**, а Compose-компонент `KeyboardView` внутри приложения (свои кнопки, свой layout-файл) — иначе нельзя гарантировать именно нашу раскладку.
* Базовая схема — стандартная корейская двух식 (두벌식) 2-буль: согласные ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅋㅌㅍㅎ, гласные ㅏㅐㅑㅒㅓㅔㅕㅖㅗㅘㅙㅚㅛㅜㅝㅞㅟㅠㅡㅢㅣ, сборка слога из джамо (Unicode Jamo Composition — тот же алгоритм, что в jamotools).
* Статус: своей реальной схемы КНДР нет → используем 두벌식 как произвольную рабочую; константы раскладки выносим в один JSON-файл `layout_kp.json`, чтобы замена на реальную схему была правкой данных, а не кода.
* Русская раскладка — ЙЦУКЕН, тоже из JSON.

## 5. Офлайн-конвейер сборки моделей (делается на ПК разработчика, не на телефоне)

1. Скачать веса: `Helsinki-NLP/opus-mt-ru-ko`, `opus-mt-ko-ru` (или NLLB-600M как план-Б), `ModelBinary` из `nth221/KoreanUnificationParallelCorpus`.
2. Конвертация в ONNX через `optimum-cli export onnx`, затем dynamic quantization INT8 (`onnxruntime.quantization`).
3. Экспорт токенов токенизатора (vocab/special tokens) в JSON для Kotlin-реализации.
4. Парсинг словарей: `dump_samhung`, `dump_biyak`, `dict.js` из `Learn-Munhwao` → единый `postdict.json` (юг→север замены).
5. Regex-правила орфоэпической конвертации (‑습니다→‑습네да и т.д.) — общий файл правил, используется и на ПК-тестах, и в APK.
6. Сборка артефактов в `app/src/main/assets/models/`.

## 6. Автоматическое тестирование (без участия людей)

### 6.1 Round-trip тесты (ядро, как договорились)
* Тестовый корпус: генерируем/берём 500–1000 русских предложений бытового и производственного содержания длиной 15–20 слов (источник — параллельные корпуса OPUS (ru-ко), берём только русскую сторону).
* Пайплайн CI (на ПК, эмулирует телефон через ONNX Runtime): `RU → SK → NK → SK → RU'`.
* Метрика совпадения — не точное равенство (round-trip никогда не даёт дословного возврата), а **семантическая близость**: косинус расстояния эмбеддингов ru-multilingual (например, `paraphrase-multilingual-MiniLM`) между RU и RU'. Порог прохода: ≥ 0.85 (калибруется на первых прогонах).
* Дополнительно — дешёвые сигналы: длина RU' в ±30% от RU, отсутствие смешения алфавитов (в RU' не должно быть хангыля), покрытие 4-граммами (BLEU-против-самого-себя как трек-метрика, не как цель).
* Каждый PR/сборка прогоняет корпус, печатает отчёт: средний скор, худшие 20 предложений, тренд относительно прошлой сборки.

### 6.2 Что делать при падении теста (расшифровка «вносить изменения»)
Диагностика по тому, где рвётся цепочка — прогоняем контрольные точки отдельно:
| Симптом | Где проблема | Что менять |
|---|---|---|
| RU→SK уже кривое (проверяется коротким тестом без моста) | базовая модель | калибровка/замена на NLLB, разбиение длинных фраз на клаузы перед переводом |
| SK→NK ломает смысл (сравниваем SK↔NK round-trip) | KoBART/пост-обработка | правила regex слишком агрессивны → ослабляем; словарь подменяет слова неверно → чистим пару в postdict.json |
| Отдельные слова-«выкидыши» (технотермины) | нет покрытия словаря | добавляем запись в Samhung/Biyak-экстракт |
| Всё ок на 10 словах, плохо на 20 | ограничение декодера | режем вход по пунктуации, переводим частями, склеиваем |

То есть «самоулучшение» = цикл: тест-пад → классификатор симптома (в CI — таблица выше в виде скрипта) → правка **данных** (словарь/regex/сегментация), не весов нейросети. Правки версионируются в git, CI подтверждает, что скор вырос и ничего не упало.

### 6.3 Почему этого достаточно без живых тестеров
Round-trip ловит *грубые* отказы (потеря смысла, мусор, неверное направление). Он НЕ ловит «неаутентичность» munhwaо — это принимается осознанно: единственный носитель качества здесь — обратная связь в бою, когда приложение уже у людей. Поэтому в UI сразу закладываем кнопку 👎 на результат перевода (сохраняет пару «вход→выход» в локальную базу; экспорт по Wi-Fi при случае — позже). Это не затрагивает процесс работы людей и даёт материал для следующей итерации словарей.

## 8. Риски (честно)

1. **KoBART-веса могут не сконвертироваться в ONNX** (генеративные BART-модели капризны). Страховка: llama.cpp-style runtime для encoder-decoder либо отказ от нейромоста SK↔NK в пользу чистой словарно-regex конвертации (качество ниже, но работает всегда). Проверка — первая задача M0.
2. **Токенизаторы Marian/BART на Kotlin** — рутина, но съест время; страховка — ONNX Runtime Extensions (есть готовые ops токенизации).
3. **Round-trip слеп к аутентичности** — принято осознанно (см. 6.3); риск закрыта только эксплуатацией.
4. **Производительность на дешёвых телефонах** — порог 6 ГБ RAM надо объявить людям до закупки/выдачи устройств.
5. **Длинные фразы 15–20 слов** — предельный режим для 600M-класса моделей; ожидаем просадку качества, лечим сегментацией (M3).
